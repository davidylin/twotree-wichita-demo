----------------------------------------

    dev/index.html · dev/style.css · dev/botdescription.txt
    (+ detail pages under dev/ when needed)

  Briefing / docs: write only in dev/botdescription.txt.

  User reviews sandbox:
    https://twotreeservices.com/wichita/dev/
    (and /dev/botdescription.txt on the host when docs change)

  Effect: host/GitHub sandbox updates. Live dashboard and production briefing
  do NOT change.

----------------------------------------

  Trigger phrases (must be explicit):
    "promote", "promote dev to prod", "ship production",
    "merge to index", "push production"

  bump production version (Section 13), then push PROD paths.

  Pairs (same filename; folder changes only):
    dev/index.html                    → index.html
    dev/style.css                     → style.css
    dev/botdescription.txt            → botdescription.txt
    dev/fire-ems-detail.html          → fire-ems-detail.html
    dev/traffic-accidents-detail.html → traffic-accidents-detail.html

  Briefing promote: copy dev/botdescription.txt → botdescription.txt as a whole,
  then retarget only the production header (File/Pair/Agents framing). Do not
  hand-maintain root botdescription.txt separately between promotes.

  On PROD copies:
    - Title without "(dev)"
    - CSS → style.css?v=X.Y.Z  (root index uses full host URL)
    - Version markers without -dev
    - detailUrl / back links use unprefixed names at root

  Live after promote:
    https://twotreeservices.com/wichita/   → index.html + style.css
    root botdescription.txt reflects the promoted briefing

  - Do not edit root PROD files while iterating — including botdescription.txt

================================================================================
4. WHAT THE APP DOES
================================================================================

Dark-themed, drag-and-drop personal dashboard for Wichita data and utilities.

Layout:
  - Grid of 300×300px widget slots (user chooses 2–24)
  - Layout + per-widget state persist in localStorage (key: wichitaDashboard)
  - First visit / bad storage → default 8-widget layout

Header:
  - Keeper of the Plains silhouette SVG
  - Title "Wichita Dashboard"
  - Subtitle "Kansas Vibe Code - vX.Y.Z" (or vX.Y.Z-dev in sandbox)
  - "App Manager LinkedIn" → https://linkedin.com/in/lindavidy
  - Hamburger → Customize modal

Core UX:
  - Drag-and-drop reorder widgets between slots
  - × on widget header removes widget (slot becomes empty)
  - Customize: slot-count slider + widget palette in category folders
  - Empty slots show "EMPTY SLOT" hint
  - Some widgets: ⓘ info popup; Fire & EMS: chart icon → detail page

5. CODE STRUCTURE (dev/index.html / index.html)
================================================================================

Monolithic HTML apps with one large <script>. Order of concerns:

  A. Shared helpers
       updateFooter, proxyFetch, createLineChart, getSundayOfWeek, getAqiStyle,
       parseReportingAreaData, buildAirQualitySnapshot, formatQueryDate,
       toLocalDayKey, getAligned14DayPeriods, fetchAllArcGISFeatures,
       build14DaySeries

  B. Widget definitions  (// Widget: Name)
       const xxxWidget = { id, title, icon, category, render, init, ... }

  C. Dashboard state
       slots[], currentSlotCount, widgetStates{}, draggedIndex

  D. allWidgets registry  (id → widget object)

  E. Persistence
       saveToStorage(), loadFromStorage()

  F. DOM / rendering
       renderEmptySlot, bindSlotEvents, bindWidgetEvents, mountWidget,
       ensureSlotCount, renderDashboard, handleDrop, removeWidget

  G. Modals & palette
       toggleModal, renderWidgetPalette, updateSlotCount,
       editQuickLinks, closeQuickLinksModal, saveQuickLinks,
       WIDGET_CATEGORIES, paletteFolderOpen, addWidgetFromPalette,
       createPaletteCard

  H. Boot
       DEFAULT_WIDGET_IDS, applyDefaultDashboard(), initDashboard()

Styles live only in the paired CSS file (not inline except minimal render()
layout). Develop in dev/style.css; promote merges into style.css.

8. DATA FETCHING
================================================================================

Three patterns: direct fetch, proxyFetch, charts.

----------------------------------------
8.1 Direct fetch() — CORS-friendly
----------------------------------------

OPEN-METEO  https://api.open-meteo.com/v1/forecast?
  lat=37.6872  lon=-97.3301  timezone=America/Chicago

  Clock:    daily=sunrise,sunset
  Weather:  current=temperature_2m,relative_humidity_2m,weather_code,wind_speed_10m
            hourly=temperature_2m,weather_code
            temperature_unit=fahrenheit, wind_speed_unit=mph
            Tabs: Current vs 4-hr Forecast; night clear ✨ / day clear ☀️
  4-Day:    daily=weather_code,temperature_2m_max,temperature_2m_min
            forecast_days=4, temperature_unit=fahrenheit
  Shared WMO conditionMap in weather + 4-day widgets.

WICHITA ARCGIS — helper fetchAllArcGISFeatures(baseUrl)
  Paginates resultRecordCount=2000 + resultOffset until exhausted.

  Violent Crime
    .../OpenData/Crime/MapServer/0/query
    Categories: MURDER, RAPE, SIM_ASSAULT, ROBBERY, AGG_ASSAULT
    Field: STARTDATETIME (epoch ms)
    Colors (oldest→newest period): #7f1d1d, #b91c1c, #ef4444

  Traffic Accidents
    .../OpenData/TrafficAccidents/FeatureServer/{layerId}/query
    layerId = year - 2017 (loop years when range spans years)
    Widget fields: ACCIDENT_DATE (epoch ms)
    Detail fields: ACCIDENT_DATE, OFFENSE_CO, OFFENSE_DE
    Colors: #92400e, #d97706, #f59e0b
    detailUrl → traffic-accidents-detail.html (top 7 offense codes × day)

  Crime + traffic both:
    getAligned14DayPeriods() → last 3 Sunday-aligned 14-day periods
    build14DaySeries(..., excludeRecentDays=3) drops trailing 3 calendar days
      (city feeds revise recent days)
    X labels "Day 1"…"Day 14"; infoMessage notes exclusion

  Fire & EMS  (wichita-fire-ems)
    .../OpenData/Fire/MapServer/2/query
    Fields: AlarmDate (epoch ms), Incident_Type, Emer_NEmer
    Window: lookbackDays=8 ending today, exclude today → past full 7 days
    UI: "Past Full 7 Days", "Total Calls", top types table
    skipTopTypes hides cancelled / no-incident labels from top list
    typeAliases shortens common CAD strings
    detailUrl → detail chart page (top 7 types × day)
    Refresh: 12 hours

----------------------------------------
8.2 proxyFetch() — CORS-blocked APIs
----------------------------------------

  POST https://ttpr.twotreeservices.com/proxy
  Body: { "targetUrl": "<absolute URL>", "method": "GET" }
  Returns a normal fetch Response (.json() / .text()).

  Use proxy for: AirNow, EIA, FRED, KSN RSS, any CORS failure.
  Do not proxy: Open-Meteo, Wichita ArcGIS.

  Air Quality — https://files.airnowtech.org/airnow/today/reportingarea.dat
    parseReportingAreaData(text, 'Wichita', 'KS') → buildAirQualitySnapshot()
    Pollutants: OZONE, PM2.5, PM10 · getAqiStyle() color bands

  Gas (EIA) — petroleum/pri/gnd weekly EPMR NUS, length 12
  Eggs (FRED) — series APU0000708111
  Potatoes (FRED) — series APU0200712112
  News (KSN) — https://www.ksn.com/news/local/feed/  (top 3 headlines)
  Platform Status — direct first, proxy on failure:
    Grok  status.x.ai (+ feed.xml)
    X     developer.x.com/api/status (JSON live monitoring; official UI data)
          fallback: docs.x.com/status HTML (legacy MDX; often a thin SPA shell)
          status link: developer.x.com/status
    Facebook / Instagram via metastatus.com/data/orgs.json

----------------------------------------
8.3 Charts — createLineChart()
----------------------------------------

  createLineChart(container, canvasId, labels, datasets)
  Destroys prior Chart instance; used by gas, egg, potatoes, crime, traffic.
  Crime/traffic: setTimeout(renderChart, 80) after innerHTML so canvas exists.
  Fire & EMS detail page builds its own Chart.js config (multi-series).

Environment: WSL2 at the repository root

----------------------------------------
14.1 Scopes (pick before git add)
----------------------------------------

  | Scope | Stage these                                              | Live? |
  |-------|----------------------------------------------------------|-------|
  | DEV   | dev/index.html, dev/style.css, dev/botdescription.txt       | No    |
  |       | + changed dev detail pages (e.g. dev/fire-ems-detail.html)|       |
  | APP   | index.html, style.css, botdescription.txt                | Yes   |
  |       | + changed prod detail pages (e.g. fire-ems-detail.html)  |       |
  | MIXED | exact paths the user lists                               | if    |
  |       |                                                          | index |

  Default after feature work: DEV, then push.
  APP only on explicit promote.

----------------------------------------
14.2 Known-good path
----------------------------------------

  1. Edit under the repository root
  2. Decide scope (ask if unclear — never guess APP)
  3. Pre-flight:
       git status · git diff --stat · git log -5 --oneline
       HTML: DOCTYPE, not empty, not PLACEHOLDER, ~90KB+ for full app
       Version markers match intent; CSS ?v= bumped if styles changed
  4. git add <named paths only>
  5. git diff --staged — confirm no extras
  6. git commit (HEREDOC message; include version on APP)
  7. git push origin main
  8. git log -1 — report SHA, scope, whether live dashboard changes
  9. Stop

----------------------------------------
14.3 Lessons learned (do not re-learn)
----------------------------------------

  1. MCP push_files / inventing file bodies destroyed production (stubs,
     PLACEHOLDER). Always commit real on-disk bytes with git.
  2. git push from WSL is the primary and sufficient deploy path.
  3. Pushing DEV updates sandbox only; live changes only when PROD files ship.
  4. Scope before staging. "push it" after sandbox work ≠ promote.
  5. Ship companion files together (HTML + CSS + briefing when each changed).
  6. Never promote WIP; still push finished DEV work so it is reviewable.
  7. Explicit paths only — never git add .
  8. One commit, one push, one verify. No force-push on main.
  9. Briefing WIP → only dev/botdescription.txt until promote. Never edit
     botdescription.txt "to keep docs in sync" outside an explicit promote
     (copy this file → botdescription.txt on promote).
 10. Do not "fix" production without an explicit user request.

----------------------------------------
14.4 Size heuristics
----------------------------------------

  index.html / dev/index.html           ~100–130 KB
  style.css / dev/style.css             ~14–30 KB
  botdescription*.txt                  ~20–50 KB
  fire-ems-detail*.html                ~15–20 KB

  Red flags: full-app HTML under ~50 KB; PLACEHOLDER / "<will be loaded>";
  unexpected junk files; staging PROD without promote.

----------------------------------------
14.5 Failure modes (quick reference)
----------------------------------------

  MCP PLACEHOLDER / stub HTML     → live site destroyed
  Editing/staging PROD for WIP    → accidental production ship
  Leaving DEV unpushed            → user cannot review on host
  index → dev/style.css            → prod depends on sandbox sheet
  Invalid JS in main script       → entire dashboard blank
  Force-push / history rewrite    → lost work
  Requiring live curl for DEV     → false "deploy failed"

15. CODING CONVENTIONS
================================================================================

DO:
  - Minimal, task-focused changes; match existing style ("// Widget: Name")
  - All new work in DEV files; push DEV when ready for review
  - Promote only on explicit request (copy pairs, don't hand-rewrite PROD)
  - saveFn(state); set lastUpdated on success; handle isLoading / error
  - e.stopImmediatePropagation() on header button clicks
  - createLineChart for Chart.js lifecycle
  - allWidgets id must match widget.id

DO NOT:
  - Edit PROD unless promote / explicit production target
  - Treat "push it" as a production ship
  - Add npm, bundlers, or frameworks without request
  - Use innerHTML += (full replace or createElement)
  - Create markdown docs unless asked (briefings are .txt only)
  - Drive-by refactors; re-add wichita-facts; MCP invent content; force-push

Large edits:
  StrReplace can fail on curly/smart apostrophes. Prefer Python with clear
  string boundaries for large removals.
